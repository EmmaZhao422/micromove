# MicroMove：Codex 插件技术评估与开发规划

版本：2026-09-25 / v0.1.0 技术预览。负责人：Emma Zhao。估时基于 1 名开发者、每天约 3–4 小时；团队素材和测试账号按时到位。

## 建议给组长的结论

**建议保留 Codex 作为首选，先做有退出条件的验证，再决定是否投入完整产品。**当前官方能力和本机安装结果不足以证明 Codex 相对 Claude Code 有“必须舍弃”的劣势；但也不足以承诺精确闹钟、原生双按钮和桌面小组件都可以仅靠插件实现。

本次已完成插件打包、本地安装和提醒引擎。后续用 2 个工作日做双平台实际事件验证。若 Codex 的提醒可见性或安装流程不满足验收且 Claude 达标，再切换宿主；Python 提醒核心保留。

## 需求基线与边界

已阅读团队 Google Docs 中明确指定的提醒 tab，并检查全文的前端介绍。需求包括 11:00 / 16:00 提醒、用户自定时间、温和文案和两个操作入口。全文介绍现有 React 19 + TypeScript + Vite 前端，数据为 localStorage；本机未取得对应源代码和资产，尚未验证该前端。

插件负责提醒和入口；已有网页继续负责动作库与跟练。默认单动作 15 秒、对称动作每边 15 秒、准备 5 秒是网页接入时应核对的较新规则，不应套用早期 30 秒版本。第一版不复制已有网页，不新建用户系统。

“桌面小组件”和“插件内提醒”是不同交付物。需求中的效果提升百分比缺少研究依据，原型不采用量化宣传。

## 平台比较

| 维度 | Codex | Claude Code | 对本项目的影响 |
|---|---|---|---|
| 插件封装 | 官方支持 skills、MCP 与 hooks；本机安装成功 | 官方支持 plugins；兼容清单已准备 | 两者都具备原型基础 |
| 工作流事件 | 官方有 SessionStart / Stop | 官方也有相应事件 | 可共用事件适配和提醒核心 |
| Hook 信任 | 安装后还需信任当前定义 | 也需主机设置和实际安装验证 | 安装摩擦需计时验证 |
| 空闲时准点提醒 | 事件机制本身不构成闹钟 | 同样不能把生命周期事件当闹钟 | 若必须准点需独立调度层 |
| 可见提醒 | 当前实现 systemMessage，界面样式待验收 | 同一输出在 Claude 的表现待验证 | 不能声称双宿主体验相同 |
| 原生双按钮/小组件 | 本次没有证明支持 | 本次没有证明支持 | 优先复用网页或单独 UI 层 |
| 成本 | 本地引擎不调用模型；宿主使用仍受账号计费/额度约束 | 同理 | 不假定“提醒必然免费” |

以上依据官方 [OpenAI 插件文档](https://developers.openai.com/plugins/build/plugins)、[Codex hooks](https://learn.chatgpt.com/docs/hooks)、[Claude Code hooks](https://code.claude.com/docs/en/hooks) 和 [Claude plugins](https://code.claude.com/docs/en/plugins)，核查日期 2026-09-25。平台会变化，正式发布前复核。本机版本是 `codex-cli 0.155.0-alpha.16.4`，不是所有用户版本的兼容承诺。

## 架构与选择理由

用户表达 → skill → Python CLI → SQLite 本机状态。

SessionStart / Stop → 只检查是否到期 → 主机提醒消息 → 用户选择现在动一下或稍后提醒 → 同一 CLI → 已配置的跟练网页。

SQLite 事务负责跨进程去重。事件输入不记录；异常返回空 JSON，既不拒绝工具，也不触发额外续跑。状态与插件安装缓存分离。暂不引入 MCP：本阶段本地操作规模很小，额外服务没有必要；待需要统一网页按钮或跨设备状态时再评估。

默认关闭，用户开启后生效。错过计划超过 30 分钟不补发，避免晚上打开工作区时补中午提醒。该窗口是工程假设，应交给小范围试用验证。

## 时间线与交付

总计约 3 周、45–60 小时（工程估算，不是已完成工时）。

| 阶段 | 工时 | 交付 | 验收 |
|---|---:|---|---|
| D1–D2 平台验证 | 6–8h | 当前原型 + 双宿主证据表 + Go/No-Go | 安装、信任、触发、关闭流程可重复 |
| D3–D5 功能闭环 | 9–12h | 团队网页入口、偏好、稍后提醒、错误处理 | 从提醒到跟练与返回可完成 |
| D6–D8 提醒体验 | 9–12h | 若必要增加独立调度及可点击 UI | 时区、休眠、勿扰及空闲行为符合约定 |
| D9–D11 小范围试用 | 9–12h | 3–5 人试用报告、问题修复 | 不重复、不打断编码，暂停可靠 |
| D12–D15 发布准备 | 12–16h | 安装说明、演示、版本与仓库整理 | 新设备复现通过，发布范围确认 |

MVP 不包含账号系统、跨设备同步、宠物养成、动作语音包和手机桌面小组件。加入任一项需重新估时。

## 决策门槛

第 2 天结束时，在同一台 Mac 和各目标主机版本上各跑 20 次到期事件；目标至少 19 次可见、零重复、零因插件造成的续跑/中断。测量 hook 本身耗时目标 P95 < 200ms（不含模型响应）。另记录新用户安装所需时间，目标 10 分钟内。

如果 Codex 在 2 天排查后仍达不到核心触发指标，而 Claude 达标，则转向 Claude。若两者都只能实现事件式提醒、而产品必须空闲准点提醒，则调整为“独立提醒组件 + 宿主入口”，不能据此判定某一个宿主不可行。

这是待执行的验收方案，不是本次已测出的统计数据。

## 风险与缓解

1. 主机 API/版本变化：固定验证版本，每次升级复测；保持引擎独立。
2. 事件提醒不准点：界面明确告知，避免伪装成闹钟；D1 决策是否另做调度。
3. 多窗口重复：SQLite 事务去重，已有并发测试。
4. 工作打扰：默认关闭，暂停优先，不 block，不自动续跑。
5. 团队网页缺失：提供入口协议并使用显式“尚未配置”状态，不伪造可用产品。
6. 首次公开项目：先私有开发；README 清楚列出实现和未实现项，不提交原始调研或凭据。
